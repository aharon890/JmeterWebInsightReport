Schema v2 for report-annotations.json, evaluation semantics, and the phase-2 report GUI. Implementation plans: plans/phase-1-assertion-engine-v2.md · plans/phase-2-asserts-gui-v2.md

Open interactive prototype →

1 · What changes and why

The report displays 13+ metrics per sampler plus run-level stats — almost none of it gateable. v2 is built on four principles:

Declared ≡ judged

Only rules you wrote decide the verdict. Everything else is reported as data, never judged. One rule on one metric of one sampler is a complete, valid gate.

Assertable ≡ displayed

Every number the report shows can be asserted — any metric, any percentile (p50…p99.99), per sampler, per group, or for the whole run.

The tester writes the direction

Bands are explicit predicates (fail: {"gt": 800}, fail: {"lt": 30}). The engine needs no per-metric direction table, so latency, throughput and apdex share one rule shape.

Mistakes are loud

JSON Schema for editor completion; load-time validation naming the rule and the fix; a rule matching nothing is a gate that never ran — it fails by default.

One engine. One rule model, one evaluator, one place a run is judged — not two code paths that phase 2 would have to render and edit twice.

2 · The schema — assertions

A new top-level array in the existing annotations file. Comments below are illustrative — the file is plain JSON.

{
  "$schema": "https://…/report-annotations.schema.json",   // IDE completion + typo squiggles
  "assertions": [
    {                                                    // the canonical check
      "id": "checkout-p90",                             // optional — auto-derived when omitted
      "description": "Contract limit §4.2",               // carried into JUnit + failure text
      "target": { "sampler": "POST /checkout" },       // exactly one target form (§3)
      "metric": "p90",
      "warn": { "gt": 1200 },                          // optional — omit = no warn band
      "fail": { "gt": 1500 }
    },
    {                                                    // a group, with direction flipped
      "target": { "match": "GET /api/*", "exclude": ["GET /api/health"] },
      "metric": "throughput",
      "fail": { "lt": 5 },                              // each match must sustain ≥ 5/s
      "tags": ["full"]                                  // -Jwir.asserts.tags=smoke skips it
    },
    {                                                    // gate the run as a whole
      "target": { "scope": "overall" },
      "metric": "apdex",
      "warn": { "lt": 0.85 }, "fail": { "lt": 0.70 }
    },
    {                                                    // any percentile; track without gating
      "target": { "match": "regex:^GET /(search|browse)" },
      "metric": "p99.9",
      "observe": true                                  // reported everywhere, never fails a build
    },
    {                                                    // stay inside a corridor
      "target": { "scope": "overall" },
      "metric": "throughput",
      "fail": { "outside": [40, 80] },              // too slow OR suspiciously fast
      "onMissing": "skip", "enabled": false          // parked, kept in the file
    }
  ]
}
Fields
idUnique; auto-derived slug(target)-metric when omitted. Names the JUnit testcase.
targetExactly one form — §3.
metricCase-insensitive; §3. p95 ≡ p95.0, median ≡ p50.
fail / warnPredicates; fail tested first. At least one required unless observe.
observeTrack the value everywhere; never gates. No bands allowed.
onMissingfail (default) · warn · skip when the target matches nothing.
enabledfalse parks a rule without deleting it (DISABLED in outputs).
tagsRule-set selection: -Jwir.asserts.tags=smoke runs matching + untagged rules.
Predicates — exactly one key per band
gt / gtebreach when actual > / ≥ value — latency, error rate
lt / ltebreach when actual < / ≤ value — throughput, apdex, sampleCount
outside[lo, hi] — breach when the value leaves the corridor. (Replaces the draft's between, which read backwards.)
Rule statuses
PASS WARN FAIL UNMATCHED→onMissing OBSERVED DISABLED INVALID (=FAIL)

Run verdict = worst status across evaluated rules. OBSERVED and DISABLED are neutral. A pattern matching several samplers evaluates each; the rule takes the worst and keeps every match, passing ones included.

3 · Targets & metric vocabulary

{"sampler": "…"}

One exact name. Naming is an explicit request — it reaches transaction children and hidden rows. samplers: […] for several.

{"match": "GET /api/*"}

Glob by default; regex: prefix for full power; optional exclude globs. Blanket selectors see top-level, non-hidden samplers only.

{"scope": "overall"}

The run as a whole: merged-distribution percentiles, total throughput, overall error rate, apdex, duration, maxThreads.

Per-sampler metrics

sampleCount · errorCount · errorRate(%) · mean · median · min · max · stdDev(ms) · throughput(/s) · apdex · p50…p99.99(ms)

Overall metrics

totalSamples · errorRate(%) · duration(s) · maxThreads · mean · median · p50…p99.99(ms) · throughput(/s) · apdex

Arbitrary percentiles ride the existing t-digest — nothing new is computed to be displayed, but any quantile can be asserted. The HTML payload always carries the grid p50/p75/p90/p95/p99/p99.9 plus every percentile a rule names, so the phase-2 editor can re-evaluate any rule client-side.

4 · Outputs & validation

CI/CD JSON — new blocks, existing keys untouched
"gate": { "status": "FAIL", "declared": 7, "failed": 2,
          "warned": 2, "passed": 2, "unmatched": 1,
          "observed": 1, "invalid": 0 },
"assertions": [ { "id": "checkout-p95", "status": "FAIL",
    "metric": "p95", "unit": "ms", "origin": "file",
    "results": [ { "sampler": "POST /checkout",
      "actual": 812, "predicate": "gt",
      "threshold": 800, "status": "FAIL" } ] } ]

Pipelines gate on jq -e '.gate.failed == 0' instead of string-matching a status that can't tell WARN from PASS. JUnit gains one testcase per rule — run-level rules included — with metric, actual, predicate and threshold in the failure text.

Validation findings — loud, named, non-fatal
  • Unknown metric → nearest-name suggestion ("p90x… did you mean p90?")
  • Target matched nothing → lists the sampler names the run actually contained
  • Bad glob / regex → position of the error
  • Band with no operator, or several; observe + bands; non-numeric threshold; outside not [lo, hi]
  • Unreachable warn band (e.g. warn > 500 with fail > 400 — fail is tested first, warn can never fire) → "swapped values?". Verdicts stay correct, so it is a warning finding in the loader; the phase-2 editor refuses to save it
  • Duplicate id; unknown keys (incl. apdexThreshold)

Every finding lands in three places: the JMeter log, the CI/CD JSON, and a notice in the report. An invalid rule renders as INVALID and counts as FAIL — the report still generates, because the report is the artifact you need to debug the config. The published JSON Schema drives editor completion; the loader guards the runtime.

5 · Phase 2 — the GUI loop

run → see every assert & verdict → tune against the observed number, verdict recomputing as you type → save the annotations file → next run gates on it. All of it inside the self-contained file:// report — save = download or clipboard, whole document, notes and unknown keys preserved. Every surface is live in the prototype:

Summary · gate strip

Verdict, its make-up (failed/warned/passed/observed) and the worst 3 breaches with actual-vs-limit — the "why" the badge never gave. Header badge itself: unchanged, always the gated verdict.

Asserts tab

Every rule: target chip, criteria, actual, verdict, matches (expandable, passing included). Unmatched rules render distinctly with a did-you-mean. Empty state teaches the feature.

Editor with live re-evaluation

One form for every metric. Targets picked from the run (typo-proof), pattern mode shows live matches; bands re-evaluate against the on-screen run as you type, stamped Preview — unsaved.

Entry points & seeding

⊕ on any metric cell pre-fills a rule from that number (fail = +20% rounded nice, warn = 80% of fail). "Generate from run" seeds a whole gate — per sampler×metric or blanket rules — as drafts to prune.

Assert from charts — the lines are the rules

Threshold lines stop being decoration: every rule targeting the charted metric draws its band as a line. Drag a line to retune that band (a draft edit with live verdict, like typing in the editor); + Assert from chart drops a new line at the clicked level and opens the editor seeded with it; clicking a series point seeds a rule for that sampler + metric. Implementable today: the report's ECharts already draws markLine thresholds, and ECharts graphic elements + click events supply drag and point-click — no backend change, everything flows into the same draft/save model. In phase 2 a chart-authored rule gates the whole-run aggregate; the chart shows the line over the series so that distinction is visible (see the prototype's Timeline tab).

Phase 3 hook: server metrics (CPU, consumer lag, heap) are pure time series, so chart-drag becomes their primary authoring surface and the time axis itself becomes assertable via an over clause that folds the series into the judged scalar — "over": {"sustainedFor": "60s"} (breach only when continuous), {"window": "30s", "agg": "avg"}; absent = whole-run aggregate, i.e. v2 semantics unchanged. Same bands, same statuses (+ INCONCLUSIVE for silent sources), targets gain {"source": "prometheus", "metric": "container_cpu_usage_seconds"} — aligned with the Server Metrics & KPI Gates design. plans/phase-3-chart-and-server-asserts.md

Draft model: edits are drafts (NEW/EDITED markers, unsaved pill, localStorage per run identity). The tab shows the would-be verdict; the header badge never lies about what this run was gated on. Chart threshold lines are the declared rules — strictest emphasized, others in the tooltip.

6 · Rollout

Phase 1 — engine (backend only)

Rule model, evaluator, validator, JSON Schema, CI/CD + JUnit outputs, payload embeds rules/results/vocabulary. plans/phase-1-assertion-engine-v2.md

Phase 2 — GUI (report only, no backend change)

Gate strip, tab, editor, seeding, drafts, save. Client evaluator = same algorithm (next-run fidelity tested end-to-end). plans/phase-2-asserts-gui-v2.md

Future, deliberately out: group-aggregate metrics (combined error rate of a matched set), cross-sampler expressions, baseline-aware rules (assert against the compared run), named threshold profiles. The rule model leaves room for each without breaking shape.
