Server Metrics & KPI Gates — Design

Collecting backend metrics after a JMeter run, aligning them to the client timeline, asserting them as KPIs, and gating CI on client / server / combined verdicts.

Proposal v1

1 · Pipeline

Collection is a separate CI step, not part of the JMeter listener. JMeter writes a run context; wir-collect waits, pulls, and writes a metrics payload; the existing -g -o generator merges it. Consequence: a crashed test still reports, distributed generators work, and metrics can be re-collected and the report regenerated without re-running the test.

Report stays offline. The collector snapshots the series into the payload at generation time; the HTML never queries Prometheus or Datadog at view time. Credentials live in CI env vars, never in the report — resolved queries are stored with secret-bearing parts redacted.

2 · Environment resolution

One config, many environments. JMeter's chosen environment travels into the run context and selects source endpoints, query variables and KPI thresholds — DEV tolerates what PROD-like does not. Everything resolvable is a variable; nothing is hardcoded per environment.

4 · Alignment & resampling

JMeter aggregates at 1s, Prometheus at 15s, Datadog rollups at 60s. Overlaying them naively invents data. The rules below are what make the two curves comparable.

{{ a.title }} {{ a.body }}
Clock skew is per source, manual, and visible. clockOffsetMs is applied on read and printed in the collection panel. A 30-second skew misattributes every spike, and nothing in the chart would tell you — so the applied offset is always shown, even when zero.

5 · KPI assertion model

One KPI = one series reduced to one number, compared against an expectation, with an explicit policy for the two ways a performance KPI goes wrong: the data was missing, or the load was not what you asked for.

Policies — the engineer decides, per KPI
onMissing
fail · warn · inconclusive · skip. A test whose whole point is Kafka lag sets fail; a nice-to-have disk metric sets skip. Inherits source-level then run-level default (inconclusive).
onLoadShortfall
invalidate · scaleBand · assertAnyway · skip. If you asked for 5 RPS and the run produced 3, a lag band of 800 msgs means nothing. scaleBand rescales the expectation by achieved/target; invalidate marks the KPI INCONCLUSIVE.
sustainedFor / breachBudget
A single 1-second CPU spike must not fail a build. Breach counts only after N consecutive seconds, or above X% of the steady-state window.
warnAt / across
WARN defaults to 80% of the threshold, matching the client-side asserts. across: max asserts the worst instance while every instance stays charted.

7 · Three gates, three verdicts

Client and server verdicts are computed independently and never collapsed. Each gate declares whether it fails the build, so a team can adopt server KPIs in observe-only mode first and turn on enforcement later.

exit 0  all enforcing gates PASS/WARN
exit 1  an enforcing gate FAILed
exit 2  INCONCLUSIVE (data missing / load invalid)
exit 3  config or source error

JUnit XML gains one test case per KPI, suite-named by gate, so Jenkins shows client and server failures separately.
